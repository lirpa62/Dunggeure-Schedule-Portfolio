# 둥그레 시간표

치지직 스트리머 둥그레의 방송 일정을 팬들과 공유하는 캘린더 웹앱입니다.
관리자가 월별 방송 일정·공지·데코·스티커를 등록하면, 방문자는 달력에서 한눈에 일정을 확인할 수 있습니다.

## 주요 기능

- 📅 **월별 캘린더 일정 관리** — 방송 일정 CRUD, 태그, 이미지 첨부
- 🎨 **캘린더 커스터마이징** — 월별 데코/스티커/공지 등록
- 🔐 **인증 & 관리자 권한** — JWT 기반 로그인, 관리자 전용 편집 API
- 🖼️ **이미지 최적화 파이프라인** — 업로드 시 WebP 변환, Cloudflare R2 저장(Supabase Storage fallback)
- 🇰🇷 **정확한 한국 공휴일/시간 처리** — `Asia/Seoul` 기준 날짜 계산, 대체공휴일 보강
- ⚡ **캐싱 & 로딩 UX** — Zustand 캐시, 스켈레톤 UI, 이미지 preload 워밍업
- 📡 **치지직 방송 기록 자동 수집** — Cloudflare Worker Cron이 1분마다 방송 시작/종료, 제목·카테고리 변경, 같이보기·드롭스·연령 제한 전환을 수집
- 🕒 **방송 타임라인** — 방송한 날의 달력 셀에만 버튼이 나타나고, 세로 레일 형태의 타임라인 팝오버로 실제 방송 흐름 표시
- 📊 **방송 결산 대시보드(`/insights`)** — 이번 달·올해·전체·직접 선택한 기간별 일정/방송 통계와 Chart.js 차트(시간대, 요일, 월별 추이, 카테고리 비중, 연속 방송 일수 등)
- 🤖 **AI 방송 결산** — Cloudflare Workers AI로 검증된 통계 fact만을 근거로 결산 문장 생성, 근거 검증 실패 시 결정적(deterministic) 요약으로 fallback
- 🗓️ **일정 편의 기능** — 같은 날짜 일정 시간순 자동 정렬(드래그 수동 정렬 유지), 이미지 전용 태그, 메모 URL 자동 링크, 커스텀 휴일(둥그레 생일)
- 🔗 **채널 바로가기** — 치지직·팬카페·유튜브·X 링크를 헤더에 배치, 모바일에서는 우측 드로어로 접고 로그인/로그아웃도 드로어 안으로 이동

> 이미지 트래픽 최적화, 자정 날짜 하이라이트 동기화, 월 전환 깜빡임 완화, AI 결산 생성 실패 대응 등 실서비스 운영 중 겪은 문제와 해결 과정은 아래 [트러블슈팅](#트러블슈팅) 섹션에 정리되어 있습니다.

## 방송 기록 수집 & AI 방송 결산

사람이 등록하는 "예정 일정"에 더해, 실제로 언제 무엇을 방송했는지를 자동으로 수집하고 이를 기간별 결산으로 보여주는 기능입니다.

### 1. 치지직 방송 기록 수집 (Cloudflare Worker)

```text
CHZZK live-detail API
  → Cloudflare Worker (1분 Cron 폴링, 이전 스냅샷과 비교해 상태 전이 판정)
  → Supabase chzzk_live_events / chzzk_live_state
```

- **왜 Cloudflare Worker인가**: Vercel Hobby의 Cron은 하루 1회라 1분 폴링이 불가능하고, 무료 VM은 유휴 인스턴스 회수 대상이라 조용히 멈출 수 있습니다. 이미 R2로 Cloudflare 계정을 쓰고 있었고, 1분 폴링(하루 약 1,440건)은 무료 한도(10만 건/일)의 약 1.5% 수준입니다.
- **중복 방지**: Worker는 실행 간 메모리가 없으므로 `dedup_key` UNIQUE 제약으로 중복을 막습니다. 이벤트를 먼저 쓰고 상태를 나중에 저장해 "유실보다 중복"이 나도록 하고, 그 중복은 DB가 흡수합니다.
- **Cron 지연/스킵 내성**: 상태 전이를 스냅샷 비교로 판정하므로 몇 번의 실행을 놓쳐도 다음 실행에서 복구됩니다.
- **시각 정확도 구분**: 방송 시작/종료는 API의 `openDate`/`closeDate`를 사용해 정확하고(`is_exact_time=true`), 제목·카테고리 변경은 폴링 감지 시각이라 최대 약 1분 오차가 있어 UI에서 `~`로 구분해 표시합니다.

**날짜 귀속 규칙** — 모든 이벤트는 해당 이벤트가 속한 **방송 세션의 시작일(KST)** 에 귀속합니다.

| 상황 | 귀속 |
|---|---|
| 3/15 02:00 시작 | 3/15 |
| 3/14 21:00 시작 → 3/15 02:00 제목 변경 | 3/14 |
| 3/14 23:57 종료 → 3/15 00:05 재시작 (8분 공백) | 3/14 |
| 3/14 23:50 종료 → 3/15 00:35 재시작 (45분 공백) | 3/15 |

직전 세션 종료 후 30분 이내에 날짜를 넘겨 재시작하면 직전 세션의 날짜를 승계합니다. 송출 사고나 잠깐의 휴식은 같은 방송으로 묶고, 자고 일어나 켠 새 방송은 분리하기 위한 규칙이며 테스트로 고정되어 있습니다.

### 2. 방송 타임라인

- 달력에서 방송 기록이 있는 날에만 버튼이 나타나므로, 버튼의 존재 자체가 "이 날 방송했다"는 표시가 됩니다.
- 셀마다 따로 요청하면 한 달에 30~42번을 호출하게 되므로, `LiveEventsProvider`가 달력에 보이는 범위를 한 번에 받아 날짜별로 나눠 씁니다.
- 같은 분에 일어난 이벤트(예: 제목과 카테고리를 함께 변경)는 하나의 노드로 묶어 무관한 사건처럼 보이지 않게 했습니다.

### 3. AI 방송 결산

```text
일정 + 방송 이벤트 + 현재 방송 상태
  → 결정적(deterministic) 세션/통계 집계
  → fact catalog (id / kind / values / priority)
  → Cloudflare Workers AI 결산 문장 생성 (각 문장에 근거 fact ID 첨부)
  → 런타임 검증 (구조 · 근거 ID · 숫자 · 일정/실제 표현)
  → 실패 시 최대 1회 repair → 그래도 실패하면 통계 기반 요약으로 fallback
  → Supabase 캐시 → UI
```

- **숫자는 AI가 만들지 않습니다**: 숫자·시간·순위·기간 비교는 모두 서버 집계 코드가 계산하고, AI에는 구조화된 fact만 전달합니다. 생성 문장의 숫자가 근거 fact에 없으면 거부합니다.
- **기간별 역할 분리**: 여러 달을 엮어 서술해야 하는 올해/전체 결산은 AI 본문을 사용하고, 하루·이번 달·직접 선택 기간은 검증된 통계 요약을 본문으로 쓰고 AI에는 숫자 없는 한 줄 평만 맡깁니다.
- **예정 vs 실제 대조**: 일정표와 방송 기록을 날짜별로 대조해 예정일에 실제로 방송한 날, 예정 시각 대비 실제 시작 시각, 합방 날 방송 길이 등을 fact로 제공합니다(자정을 넘긴 방송도 실제 시점으로 환산).
- **데이터 최소화**: 메모, URL, 개별 일정의 멤버 전체 목록, raw row는 AI에 보내지 않으며, 일정 제목은 신뢰할 수 없는 입력으로 취급합니다. API 토큰과 service role key는 서버 라우트에서만 사용합니다.
- **비용 제어**: 캐시 키는 `기간 + SHA-256(입력) + 모델 + 프롬프트 버전`이라 같은 통계는 모든 사용자가 재사용합니다. 프로세스 내 single-flight와 DB lease로 서로 다른 서버리스 인스턴스의 동시 요청을 하나의 AI 호출로 합치고, Supabase RPC로 하루 요청 수(기본 50회)를 원자적으로 예약합니다.
- **장애 시에도 통계는 정상 표시**: AI 비활성화, quota 초과, timeout, 잘못된 응답이 발생해도 통계 대시보드는 그대로 동작합니다.
- **모델 평가 스크립트**: 합성 데이터를 실제 production 집계 경로로 통과시킨 fixture로 후보 모델을 비교합니다. 예상 사용량(Neurons)이 예산 상한을 넘으면 실행 전에 거부합니다.

## 시작하기

### 1. 의존성 설치

```bash
npm install
```

### 2. 환경변수 설정

`.env.local` 파일에 아래 값을 입력합니다.

- Supabase URL, Anon Key, Service Role Key
- 관리자 초기 비밀번호
- JWT Secret
- 이미지 업로드를 R2로 저장하려면 R2 환경변수
- AI 방송 결산을 사용하려면 Cloudflare Workers AI 환경변수 (`SCHEDULE_AI_ENABLED=false`이면 credential 없이 개발 가능)

### 3. 개발 서버 실행

```bash
npm run dev
```

## Supabase 마이그레이션

Supabase CLI는 프로젝트 devDependency로 설치되어 있으므로 `npx` 또는 `npm run`으로 실행할 수 있습니다.

### 최초 연결

```bash
npm run db:login
npm run db:link -- --project-ref <project-ref>
```

### 새 마이그레이션 생성

```bash
npm run db:new -- add_example_table
```

생성된 SQL 파일은 `supabase/migrations/` 아래에 추가됩니다.

### 원격 DB에 적용


### 적용 상태 확인

```bash
npm run db:list
```

기존 호환용으로 `npm run db:migrate`도 `supabase db push`를 실행합니다.

## 이미지 R2 마이그레이션

기존 Supabase Storage에 올라간 일정/스티커/프로필 이미지는 R2 환경변수 설정 후 아래 명령으로 이전할 수 있습니다.
데코 원본 이미지 컬럼이 필요하므로 먼저 `npm run db:push`로 최신 마이그레이션을 적용하세요.

### 대상 확인

```bash
npm run migrate:images-to-r2
```

### 실제 적용

```bash
npm run migrate:images-to-r2 -- --apply
```

마이그레이션 대상은 `schedules.image_url`, `calendar_decorations.image_url/storage_path/original_image_url/original_storage_path`, `stickers.url/storage_path`, `users.avatar_url/avatar_path`입니다. 기본 실행은 `dry-run`이며, `--apply`를 붙여야 R2 업로드와 DB 업데이트가 진행됩니다.

데코 이미지는 일정표 표시용 WebP와 확대 보기용 원본을 함께 저장합니다. 스티커, 일정/공지 업로드 이미지, 프로필 이미지는 GIF를 제외하고 WebP로 최적화해 저장합니다.
월별 공지/데코 메타데이터와 스티커 목록은 Zustand 캐시를 사용해 월 이동과 스티커 팝업 재진입 시 먼저 보여주고 백그라운드에서 갱신합니다.

## 트러블슈팅

### Supabase Storage cached egress 한도를 빠르게 초과하는 경우

증상:

- Supabase 배포 4일 만에 Storage cached egress가 `6.86 / 5 GB (137%)`까지 올라 무료/기본 한도를 초과했습니다.
- 일정표는 이미지가 많은 캘린더 화면이라 새로고침, 월 이동, 팝업 재진입이 반복되면 이미지 트래픽이 빠르게 누적됩니다.

원인:

- 일정 이미지, 데코 이미지, 스티커, 프로필 이미지가 Supabase Storage public URL로 직접 제공되면 이미지 조회 트래픽이 Supabase cached egress로 집계됩니다.
- 데코 원본 이미지와 표시용 이미지처럼 같은 콘텐츠를 여러 용도로 보여주는 경우에도 조회량이 쉽게 늘어납니다.

대응:

- 이미지 저장소를 Cloudflare R2로 이전하고 DB의 이미지 URL과 storage path를 R2 기준으로 갱신했습니다.
- `scripts/migrate-supabase-images-to-r2.mjs`로 기존 `schedules`, `calendar_decorations`, `stickers`, `users` 이미지 데이터를 dry-run 후 `--apply`로 이전합니다.
- 업로드 API는 R2 환경변수가 있으면 R2에 저장하고 없으면 기존 Supabase Storage 경로를 fallback으로 사용합니다.
- GIF를 제외한 업로드 이미지는 WebP로 최적화하고 데코 이미지는 일정표 표시용 WebP와 확대 보기용 원본을 분리 저장합니다.

마이그레이션 후 관찰값:

- Cloudflare R2 `Class A Operations`: 170
- Cloudflare R2 `Class B Operations`: 16.58k

주의:

- R2 전환 후에도 이미지 URL은 변경 시 새 URL을 발급하는 방식을 유지해야 브라우저 장기 캐시(`immutable`)로 인한 이전 이미지 노출을 피할 수 있습니다.
- Supabase Storage fallback 경로를 계속 유지하므로, R2 환경변수 누락 시 다시 Supabase egress가 증가할 수 있습니다.

관련 커밋:

- `feat: 이미지 저장소 R2 연동 및 날짜 표시 안정화`
- `feat: 이미지 R2 마이그레이션 및 최적화 캐싱 개선`

### 자정 이후 오늘 하이라이트가 이전 날짜에 남는 경우

증상:

- 23:59에서 00:00으로 넘어가는 순간에는 오늘 하이라이트가 새 날짜에 정상 적용됩니다.
- 이전/다음 달에서 `오늘` 버튼을 클릭해도 새 날짜 하이라이트가 정상 적용됩니다.
- 하지만 자정 직후 새로고침하면 캐시된 초기 HTML 또는 하이드레이션 상태 때문에 이전 날짜에 `calendar-day-today`가 남아 보일 수 있습니다.

원인:

- 캘린더 셀의 오늘 판정이 React state인 `todayDate` 또는 서버/캐시 HTML의 초기 렌더 상태에 영향을 받으면, 자정 직후 새로고침 시 이전 날짜 class가 먼저 노출될 수 있습니다.
- Next.js가 내려준 초기 HTML과 클라이언트의 실제 한국 시간 계산이 어긋나는 짧은 구간에서는 `useEffect` 동기화가 실행되기 전까지 잘못된 하이라이트가 보일 수 있습니다.

대응:

- 한국 날짜 계산은 `Intl.DateTimeFormat`의 `Asia/Seoul` 기준으로 수행합니다.
- `visibilitychange`, `focus`, `pageshow`, 한국 자정 타이머에서 오늘 날짜를 다시 동기화합니다.
- 캘린더 셀의 오늘 판정은 렌더 시점의 `getKoreaToday()` 값을 사용합니다.
- 최종적으로 오늘 하이라이트 class는 클라이언트 마운트 이후에만 계산해 캐시된 초기 HTML의 이전 날짜 class가 노출되지 않도록 합니다.

관련 커밋:

- `fix: 오늘 날짜 표시 동기화 보강`
- `fix: 오늘 하이라이트 렌더 기준 보정`
- `fix: 새로고침 시 이전 날짜 하이라이트 방지`

### 일정은 보이는데 스켈레톤 UI가 계속 남는 경우

증상:

- 새로고침 후 이번 달 일정 텍스트와 이미지 일부가 이미 그려졌는데도 빈 일정 칸에 스켈레톤 UI가 계속 표시됩니다.

원인:

- 일정 API 응답 후 이미지 preload가 끝나야만 `isSchedulesLoading`이 false가 되는 구조에서는 이미지 로딩이 지연되거나 브라우저 캐시의 `load` 이벤트를 놓치면 로딩 상태가 오래 유지될 수 있습니다.

대응:

- 일정 데이터 응답을 받으면 이미지 preload 완료 여부와 무관하게 즉시 `isSchedulesLoading`을 false로 바꿉니다.
- 이미지 preload는 백그라운드 워밍업으로만 처리합니다.
- `LoadingImage`는 `img.complete`와 `naturalWidth`를 확인해 캐시된 이미지의 `load` 이벤트 누락에도 스켈레톤을 종료합니다.

관련 커밋:

- `fix: 일정 로딩 스켈레톤 종료 조건 보강`

### 월 전환 시 이미지가 깜빡이는 경우

증상:

- 한 번 본 달로 다시 이동해도 일정/데코 이미지는 캐시된 것처럼 빨리 보이지만 월 전환 순간 이미지가 잠깐 투명해지거나 스켈레톤이 보입니다.

원인:

- 월별 일정/데코 데이터와 브라우저 이미지 파일은 캐시되지만 `LoadingImage`의 `loaded` 상태는 컴포넌트 로컬 state라 월 전환으로 언마운트/리마운트되면 다시 false에서 시작합니다.

대응:

- 이미지 `src`별 로드 완료/실패 상태를 메모리 Set에 기록합니다.
- preload가 끝난 이미지도 같은 Set에 기록합니다.
- 이미 본 `src`는 `LoadingImage`가 처음부터 loaded 상태로 렌더링해 스켈레톤과 opacity 전환을 다시 거치지 않게 합니다.

주의:

- 이 캐시는 이미지 파일 내용을 저장하지 않고 `src`가 이미 처리됐다는 UI 상태만 저장합니다.
- 현재 업로드 코드는 `Date.now()`와 `crypto.randomUUID()`로 매번 새 이미지 URL을 만들기 때문에 이미지 교체 시 새 URL이 표시됩니다.
- 나중에 같은 URL에 파일만 덮어쓰는 방식으로 바꾸면 브라우저의 장기 캐시(`immutable`) 때문에 이전 이미지가 보일 수 있으므로 이미지 변경 시에는 새 URL을 유지하는 것이 안전합니다.

관련 커밋:

- `fix: 월 전환 시 캐시 이미지 깜빡임 완화`

### AI 결산 응답이 JSON 중간에서 끊기는 경우

증상:

- 전체 기간 결산에서 모델이 같은 문장을 반복하다 출력 토큰 상한(768)에 도달해 JSON 문자열이 문장 중간에서 끊겼습니다.
- 재생성을 해도 기존 오류를 고치지 않고 다른 오류가 있는 응답을 새로 만드는 경우가 있었습니다.

원인:

- 연간/전체 결산은 입력 fact가 많아 출력 예산이 부족했고, 반복 억제 파라미터가 없었습니다.
- 재생성 요청에 오류 메시지만 전달하고 실패한 응답은 전달하지 않아 모델이 무엇을 고쳐야 하는지 알 수 없었습니다.

대응:

- 출력 예산을 짧은 기간 1,024 / 연간·전체 1,536 토큰으로 조정하고 `repetition_penalty 1.1`, 문단당 근거 ID 최대 8개로 반복을 제한했습니다.
- repair 요청에 오류와 길이 제한된 이전 응답을 신뢰할 수 없는 user 데이터로 전달하고, 최대 1회 재생성 원칙은 유지했습니다.
- provider 로그에는 completionTokens, maxTokens, JSON 유효성, 잘림 가능성만 남기고 생성 원문과 credential은 기록하지 않습니다.

관련 커밋:

- `fix: AI 결산 생성 실패 진단과 v10 수정`

### AI 결산에 내부 영어 토큰이 그대로 노출되는 경우

증상:

- 결산 본문에 "2026년 9월 6일부터 partial로 수집되었으며"처럼 영어 토큰이 그대로 나왔습니다.

원인:

- `partial`, `unavailable`, `scheduled_not_confirmed`는 모델이 지어낸 말이 아니라 서버가 AI 입력에 그대로 넣은 enum 값이었습니다. 프롬프트에 표현 규칙을 적어도 구조적으로 새어 나왔습니다.

대응:

- AI 입력의 내부 토큰을 모델이 그대로 옮겨 적어도 문장이 되는 한국어 설명으로 투영했습니다.
- 동시에 8B 모델은 근거 fact와 문장을 연결하지 못해 합성 4개 범위가 모두 fallback되었고, 같은 입력에서 70B는 3개가 통과해 기본 모델을 70B로 올렸습니다. 모델은 환경변수 하나로 되돌릴 수 있습니다.

관련 커밋:

- `fix: AI 입력의 내부 토큰을 한국어로 바꾸고 기본 모델을 70B로 올림`

### 짧은 기간 결산에서 AI가 근거와 다른 수치를 쓰는 경우

증상:

- 실데이터 월간 결산에서 "등록 일정은 16개로 2026년 8월보다 24개 줄었습니다"처럼 근거와 어긋난 수치가 생성되어 검증에 걸렸습니다.

원인:

- 정확성, 문장 품질, 성공률을 AI 하나에 동시에 요구하는 구조였습니다.

대응:

- 하루·월·직접 선택 기간은 검증된 통계 요약을 본문으로 사용하고, AI에는 숫자를 쓸 수 없는 한 줄 평만 맡겼습니다. 한 줄 평이 실패하면 그 줄만 비우므로 본문에 영향이 없고, 입력도 상위 6개 fact로 줄여 비용을 낮췄습니다.
- 여러 달을 엮어야 하는 연간/전체는 AI 본문을 유지합니다.
- 70B가 숫자는 맞게 썼지만 근거 fact ID를 빠뜨려 fallback되던 경우는, 값이 입력에 실제로 있고 단위가 맞을 때만 근거를 자동 보정해 근거 없는 숫자는 계속 차단합니다.

관련 커밋:

- `feat: 짧은 기간은 통계 요약 + AI 한 줄 평으로 전환`
- `feat: 결산을 방송 패턴과 예정·실제 대조 중심으로 개선`

### AI 결산 실패 시 매번 재시도해 비용과 대기 시간이 반복되는 경우

증상:

- 같은 기간을 열 때마다 AI를 두 번씩 다시 호출해, 연간 결산에서 매번 약 30초를 기다리고 약 600 Neurons를 쓴 뒤 결국 통계 요약으로 떨어지는 일이 반복되었습니다.

원인:

- 생성 실패 시 lease row를 삭제해 다음 요청이 곧바로 새 생성을 시도했습니다.

대응:

- 실패 row를 `failed` 상태로 남기고 `lease_expires_at`을 재시도 가능 시각(6시간 후)으로 사용합니다. 그 전까지는 즉시 통계 요약을 보여줍니다.
- 새 방송 기록이 들어와 통계가 바뀌면 입력 hash가 달라져 새 row가 되므로 6시간과 상관없이 다시 시도합니다.
- 마이그레이션 적용 전에는 예전처럼 lease를 삭제하도록 처리해 배포 순서와 무관하게 동작하게 했습니다.

관련 커밋:

- `fix: AI 결산 생성 실패를 6시간 캐시해 매번 재시도하지 않게`

### 모바일 드로어가 헤더 높이에 갇혀 잘리는 경우

증상:

- 좁은 화면에서 채널 바로가기 드로어를 열면 드로어 높이가 네비게이션 바(58px)에 갇혀 내용이 잘리고, 오버레이도 헤더 영역만 덮었습니다.

원인:

- 네비게이션 바의 `backdrop-blur`(backdrop-filter)가 `position: fixed` 자식의 containing block이 되어, 드로어가 뷰포트가 아닌 nav 기준으로 배치되었습니다.

대응:

- 드로어를 포털로 `body`에 붙여 nav의 containing block에서 벗어나게 했습니다.
- 데스크톱/모바일 전환은 화면 폭을 JS로 재지 않고 CSS breakpoint로 처리해 SSR에서도 맞는 쪽이 바로 보이게 했습니다.

관련 커밋:

- `feat: 헤더에 둥그레 채널 바로가기 추가`

### 기능 철회 판단: 승부예측(통나무파워) 수집

- 공개 통계(시작·마감 시각, 총 통나무파워, 선택지별 비율)를 수집하는 기능을 구현했지만, 정답(`winningOptionNo`)은 로그인이 필요한 상세 API에서만 제공되어 Worker에서 결과를 채울 수 없었습니다.

관련 커밋:

- `revert: 승부예측 수집 제거`
